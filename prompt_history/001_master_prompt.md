## 5. DATA MODEL

Define a primary key for every entity, foreign keys for every relationship, cardinality, optional relationships, effective dates, and lifecycle states. Core entities:

Supporting tables (needed to satisfy "bridge tables for N:M", "calendars", and "do not overwrite history"):

- `CarrierCalendar` and `FacilityCalendar` (open/close hours, holidays, effective_from/effective_to)
- `WeatherEventFacility` and `WeatherEventLeg` bridge tables (N:M: a storm affects many facilities/legs, and a leg can meet many storms)
- `ShipmentDelayReason` bridge table (N:M between Shipment/Leg and DelayReason, with `delay_hours_attributed`)
- `ShipmentStatusHistory` (append-only lifecycle records, never overwrite)
- `RouteChange` (append-only record when a shipment is rerouted: old route, new route, reason, effective_time)

Document for every field: type, required/optional, allowed values, units, uniqueness, validation rule. Put this in `docs/DATA_DICTIONARY.md` and also emit a machine-readable `schema.json`.

Key fields to include (extend as needed):

## 8. GENERATION PIPELINE (order matters, parents before children)

Step 1. Write the data dictionary first (docs + schema.json).
Step 2. Master data: Carrier, Facility, ServiceLevel, Route + RouteLegTemplate, carrier/facility calendars.
Step 3. Disruptions: WeatherEvent windows and facility disruption windows, with bridge tables to facilities/legs.
Step 4. Shipments: pick service level, route, created_at, promised_delivery_at = created_at + target_hours (respect calendars).
Step 5. Legs: planned times from route templates and carrier speeds; respect facility opening hours.
Step 6. Simulation (the heart of the project). For each leg compute actual times with an explicit, documented formula, for example:

```
actual_transit = planned_transit * carrier_noise * weather_multiplier(overlapping windows)
facility_wait  = f(queue_length, throughput, calendar_closures)
actual_arrive  = actual_depart + actual_transit
next_depart    = max(actual_arrive + facility_wait, next_open_time)
```
Reroutes happen with a probability driven by severe weather or long queues, and append a `RouteChange` record plus new/updated legs (never overwrite history; supersede with effective dates).
Step 7. Tracking events from the simulation: PICKED_UP, DEPARTED, ARRIVED, DELAY_SCAN, ROUTE_CHANGED, OUT_FOR_DELIVERY, DELIVERED. Every event has `event_time` and a later `ingestion_time` (ingestion lag drawn from a documented distribution, with a heavy tail for late-arriving data). Add duplicates (same event re-ingested) and event gaps (missing scans).
Step 8. Derive labels from source records: actual_delivery_at from the DELIVERED event, `delay_hours = actual - promised`, label via ServiceLevel rules (ON_TIME if delay <= grace_hours, DELAYED, SEVERELY_DELAYED by thresholds). Shipment status is derived from the event history via ShipmentStatusHistory.
Step 9. DelayReason attribution: decompose delay into weather, queue, carrier, calendar, and reroute components that sum to total delay (arithmetic reconciliation). Write `ShipmentDelayReason` rows.
Step 10. ETA snapshots at defined prediction times (e.g. at creation, after pickup, after each leg arrival, and T-24h, T-12h, T-6h before promised time). Use ONLY events with `ingestion_time <= prediction_time` and calendars/weather forecasts known at that time.
Step 11. Inject labelled anomalies (section 9) and write `ground_truth`.
Step 12. Validate (section 10), export (section 12), then run the reproducibility check (section 11).

Rule: outcomes and labels come from the simulation and rules above. No independent `random.choice` for derived fields.

## 9. REQUIRED EDGE CASES (labelled, not silent)

Inject each at a small documented rate (e.g. 0.3% to 1% of affected rows) and never corrupt unrelated rows:

1. EVENT_TIME_INGESTION_CONFUSION: a row where ingestion_time and event_time are swapped or event_time is replaced by ingestion_time.
2. IMPOSSIBLE_ROUTE_ORDER: legs whose sequence or timestamps are impossible (arrival before departure, leg 2 starts before leg 1 ends, facility visited out of route order).
3. ETA_USES_FUTURE_EVENT: an ETAEstimate whose `features_cutoff_time` or event usage includes events ingested after prediction_time.
4. DELIVERED_STILL_IN_TRANSIT: shipment has a DELIVERED event but `current_status` is IN_TRANSIT (or events continue after delivery).

Also include boundary and failure cases: delay exactly equal to grace_hours, delivery at midnight/cutover, shipment with zero tracking events after pickup, all events late-arriving, facility closed on holiday, cancelled shipment, reroute during severe weather.

Each anomaly row carries `issue_type` in a SEPARATE `ground_truth` file only (columns: record_type, record_id, issue_type, description, expected_decision, injected_field, original_value, injected_value). The input tables must NOT contain any column that reveals the anomaly. Add a test that fails if any ground-truth-only column leaks into feature/input tables.
